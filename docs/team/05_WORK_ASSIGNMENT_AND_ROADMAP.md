# KReports 업무 배분 및 2026년 9월 16일 제출 로드맵

## 1. 기본 전제

KJ, YE, EI는 사람과 역할을 구분하는 표기입니다. 신규 개발 Branch 이름이
아닙니다.

| 사람 | 역할 | 기본 책임 |
|---|---|---|
| KJ | 제품·데이터 총괄 | 공용 DB, 공통 구조, MCP, 통합, 출시, 최종 제출 |
| YE | 4년차·부팀장 | 사업보고서 본문, 사업·재무·Peer 분석, 회계 리뷰 |
| EI | 2년차 | 감사보고서 패키지, 재무제표·주석, KAM·감사절차 |

신규 업무는 다음과 같은 작업단위 Branch로 진행합니다.

```text
feat/10-audit-package-note-source
feat/11-business-report-analysis
fix/15-wrong-dart-link
docs/16-submission-report
```

기본 협업 단위는 다음과 같습니다.

```text
하나의 Issue
→ 하나의 작업 Branch
→ 하나의 Primary Assignee
→ 하나의 PR
→ Review와 승인
→ main Merge
→ Branch·Worktree 정리
```

`감사보고서 패키지`는 감사인의 의견 본문뿐 아니라 첨부된 감사대상
재무제표, 현금흐름표·자본변동표, 재무제표 주석, 회계정책, 중요한 추정과
판단, KAM과 감사절차를 포함합니다. 재무제표 주석의 기본 원천은
감사보고서 패키지입니다.

## 2. 프로젝트의 두 가지 목적

### 2.1 제품 목적

2026년 9월 16일까지 다음 흐름을 반복 가능하게 보여주는 MVP(Minimum
Viable Product, 사용자가 실제 가치를 확인할 수 있는 최소 완성 제품)를
준비합니다.

```text
DART 사업보고서·감사보고서 패키지·수시공시
→ 구조화된 읽기 전용 데이터베이스
→ MCP 검색·분석 기능
→ 챗봇의 자연어 질문과 근거 기반 답변
→ DART 원문 재확인
```

단순히 한 회사에서만 성공하는 화면을 만드는 것이 아니라 다음을 확인합니다.

- 여러 대표회사에서 같은 질문 흐름이 작동함
- 회사·연도·연결/별도와 접수번호가 맞음
- 원문과 분석 결과를 함께 확인할 수 있음
- 자료 미확보를 `공시하지 않음`으로 단정하지 않음
- 동일한 코드와 Runtime DB에서 영상과 설명서를 재현할 수 있음

### 2.2 인력 육성 목적

YE와 EI 모두 다음 AI 빌딩(AI를 이용해 실제 기능을 설계·구현·검증하는
과정)을 경험합니다.

1. 사용자 문제 정의
2. 기존 구조와 E2E 데이터 흐름 조사
3. 기존 코드·표·Test의 Reuse Map 작성
4. AI에게 범위가 명확한 작업 지시
5. AI가 만든 코드와 결과 이해·수정
6. 자동 Test 작성·실행
7. 실제 DART 원문 대조
8. Commit·PR·Review
9. 챗봇 시연
10. 다른 사람 기능 교차 리뷰

단순 원문 대사, 자료정리 또는 화면 캡처만으로 업무를 완료하지 않습니다.
담당자는 자신이 변경한 입력, 원천, 규칙, 결과, 실패 동작과 검증 근거를
직접 설명할 수 있어야 합니다.

## 3. 공동 운영 원칙

### 3.1 데이터베이스

- 공용 데이터베이스의 수집·수정·구조 변경·출시는 KJ만 수행합니다.
- YE와 EI는 승인된 공용 데이터베이스 전체를 읽기 전용으로 조회합니다.
- 개발과 자동 Test는 임시 Test DB와 Fixture를 사용합니다.
- 데이터 오류는 공용 DB 행을 직접 고치지 않습니다.
- 오류를 만든 Collector, Parser, 변환 또는 Analysis 코드를 고치고 회귀
  Test를 추가한 뒤, KJ가 공용 데이터를 재생성합니다.
- Schema, Migration, Backfill, Runtime DB Export와 Release Manifest 작업은
  대상과 영향이 확인되고 명시적으로 승인된 경우에만 실행합니다.

### 3.2 GitHub

- `main`에 직접 작업하거나 Push하지 않습니다.
- 하나의 Issue를 하나의 작업 Branch와 PR로 처리합니다.
- Branch는 최신 승인된 `main`에서 만듭니다.
- 신규 업무에 `kj`, `ye`, `ei`와 같은 사람별 장기 Branch를 사용하지
  않습니다.
- 한 사람당 활성 작업 Branch는 원칙적으로 하나입니다.
- 무관한 문제를 발견하면 같은 PR에 넣지 않고 새 Issue로 분리합니다.
- 변경사항은 작은 Commit으로 기록하고 확인한 파일만 Stage합니다.
- Draft PR로 진행상태와 방향을 조기에 공유합니다.
- 수정 요청 시 Worktree를 원복하지 않고 같은 Branch에 수정 Commit을
  추가합니다.
- 승인된 변경만 `main`에 Merge합니다.
- Merge 후 완료된 Branch와 Worktree를 정리하고 다음 업무는 최신 `main`에서
  새로 시작합니다.

### 3.3 기능 완료

기능 완료는 다음을 모두 포함합니다.

- 사용자 문제와 완료조건 충족
- 코드 또는 문서 변경
- 기존 기준 코드 재사용과 중복 구현 확인
- 자동 Test
- 실제 DART 원문 대조
- 데이터 출처와 한계 확인
- MCP 결과 확인
- 챗봇 사용자 답변 확인
- 담당자의 쉬운 설명
- PR과 교차 Review
- 관련 문서·영상·설명서 영향 반영

## 7. 공동 대표 기능 — 수익인식 E2E 분석

대표 제출 Scenario는 두 보고서 영역을 하나의 답변으로 연결합니다.

### 사용자 질문 예

> “A사의 수익인식 회계정책과 관련 주석을 보여주고, 감사인이 매출을
> 핵심감사사항으로 선정했는지, 어떤 감사절차를 수행했는지 원문 근거와 함께
> 알려줘.”

### YE 제공 영역

- 사업보고서상 제품·서비스와 매출구조
- 주요 고객·계약·사업위험
- 매출·이익·현금흐름 추이
- 매출 관련 수시공시

### EI 제공 영역

- 감사보고서 패키지의 수익인식 회계정책
- 매출 관련 재무제표 주석
- 매출 관련 KAM
- KAM 선정 이유
- 감사인의 주요 절차
- 감사보고서 원문과 접수번호

### KJ 제공 영역

- 동일 회사·사업연도·연결/별도 연결
- DB Source 우선순위와 품질 상태
- MCP Tool 호출과 답변 통합
- DART 링크와 사용자 표현 통일
- Release Candidate 고정

### 작업 Branch 예

```text
feat/20-revenue-recognition-e2e
```

Primary Assignee는 한 명으로 두고, 다른 사람은 회계·원천·DB·MCP Reviewer로
참여합니다.

## 11. 9월 10일 MVP 완료 기준

### 데이터

- 동일한 승인 Runtime DB 버전을 사용함
- YE·EI는 읽기 전용으로 접근함
- 회사·연도·연결/별도와 Source 상태가 기록됨
- 감사보고서 패키지 우선 주석 Source가 대표 범위에서 확인됨

### 사업·재무 기능

- 사업 내용·매출구조·위험·계약 조회가 가능함
- 재무·현금흐름·Peer 결과가 정상임
- 사업보고서 본문과 실제 원문이 연결됨

### 감사보고서 패키지 기능

- 감사대상 재무제표·주석과 회계정책을 조회할 수 있음
- 감사의견·KAM·선정 이유·감사절차가 구분됨
- 여러 KAM이 각각 표시됨
- 실제 감사보고서 패키지와 접수번호가 일치함

### 통합 기능

- 사업 내용·재무·수익인식 주석·KAM·감사절차가 한 질문 흐름에서 연결됨
- 원문 링크로 결과를 재확인할 수 있음
- 자료 미확보 시 잘못된 결론을 내리지 않음

### 협업·학습

- YE와 EI가 각각 최소 하나의 작업단위 PR을 제출함
- 각자 자동 Test와 실제 DART 검증을 수행함
- 각자 E2E 흐름과 AI 판단을 설명함
- 서로의 기능을 교차 Review함
- Merge된 Branch와 Worktree가 정리됨

## 12. 핵심 정렬 문장

> 공용 데이터베이스는 KJ가 통제하고, YE와 EI는 전체 승인 데이터를 읽기
> 전용으로 사용한다.

> 원천 책임은 보고서 영역별로 나누되, 사용자 기능은 보고서를 넘나드는 E2E
> 단위로 완성한다.

> Branch는 담당자의 개인 공간이 아니라 하나의 Issue를 해결하기 위한
> 일회성 변경 묶음이다.

> AI가 코드를 만들더라도 담당자가 원천, 규칙, 결과와 검증 근거를 직접
> 설명할 수 있어야 완료다.
