# KReports 팀 오리엔테이션 진행안

## 1. 오리엔테이션의 대상과 목적

이 오리엔테이션은 KJ, YE, EI 세 사람이 함께 진행합니다. 개발자가 기술
구조를 일방적으로 설명하는 자리가 아니라, 회계사 팀원이 KReports의 기능을
직접 맡아 AI를 활용해 개선하기 위한 공동 출발점입니다.

오리엔테이션이 끝났을 때 각 참석자는 다음을 설명할 수 있어야 합니다.

1. KReports가 해결하려는 업무상 문제
2. 사업보고서와 감사보고서 패키지의 차이
3. 데이터가 DART에서 챗봇 답변까지 이동하는 전체 흐름
4. 공용 데이터베이스를 누가 관리하고 다른 담당자가 어떻게 조회하는지
5. MCP가 챗봇과 KReports 사이에서 하는 역할
6. Issue별 작업 Branch와 Worktree에서 작업하고 PR을 제출하는 방법
7. PR 수정 요청과 Merge 후 Branch·Worktree를 어떻게 처리하는지
8. 자신이 9월 16일까지 책임질 기능과 결과물
9. AI가 만든 코드와 결과를 어떻게 검증해야 하는지

## 4. 1부 — 해결하려는 업무상 문제

회계사나 감사인이 특정 회사의 수익인식, 위험 또는 감사 이슈를 검토할 때
보통 다음 과정을 반복합니다.

```text
DART에서 회사 검색
→ 사업보고서 열기
→ 사업의 내용과 매출구조 찾기
→ 감사보고서 제출물 열기
→ 첨부 재무제표와 주석 찾기
→ 감사의견과 핵심감사사항 찾기
→ 관련 주석 번호와 감사절차 연결
→ 전기 또는 비교회사 자료 다시 검색
→ 출처를 조서나 보고서에 정리
```

문제는 자료가 없다는 것이 아니라 다음과 같습니다.

- 제출물과 첨부문서가 나뉘어 있음
- 회사명·접수번호·사업연도·연결·별도를 다시 맞춰야 함
- 같은 주제를 여러 회사에서 반복 검색해야 함
- 원문을 찾은 뒤 사람이 다시 연결하고 요약해야 함
- 일반 챗봇의 답변은 실제 원문과 출처를 확인하기 어려울 수 있음
- 담당자의 경험에 따라 검색 범위와 결과가 달라질 수 있음

### KReports의 한 문장 정의

> KReports는 DART의 사업보고서·감사보고서 패키지·수시공시를 구조화하고,
> 챗봇이 MCP를 통해 필요한 검색과 분석을 호출하여 원문 근거와 함께
> 답하도록 만드는 공시 분석 기반입니다.

## 5. 2부 — POC와 MVP의 차이

### POC

POC(Proof of Concept, 아이디어가 기술적으로 가능한지 보여주는 시험)는
특정 회사 한 곳에서 한 번 잘 작동하는 정도로도 의미가 있습니다.

예:

- 준비한 회사의 KAM을 한 번 찾아 보여줌
- 미리 만든 화면에서 결과를 시연함

### MVP

MVP(Minimum Viable Product, 사용자가 반복해서 사용하며 가치를 확인할 수
있는 최소 완성 제품)는 다음 조건이 더 필요합니다.

- 여러 회사와 연도에서 같은 질문 구조를 사용할 수 있음
- 자료가 없거나 일부만 있을 때 제한을 설명함
- 결과의 원문과 접수번호를 다시 확인할 수 있음
- 같은 데이터와 코드에서 반복 가능한 결과가 나옴
- 기능을 다른 사람이 실행하고 설명할 수 있음
- 변경사항이 Test와 Review를 거침

이번 제출은 영상만 그럴듯하게 만드는 POC가 아니라 이후 계속 발전시킬 수
있는 MVP를 목표로 합니다.

## 6. 3부 — 보고서 원천 기준

### 사업보고서

사업보고서(Business Report, 회사가 사업·위험·주요 계약·지배구조 등의
법정 공시를 종합해 제출하는 보고서)는 다음 정보의 기본 원천입니다.

- 사업의 내용
- 제품과 서비스
- 매출·매입 구조
- 연구개발
- 위험
- 주요 계약
- 지배구조와 기타 사업 공시

### 감사보고서 패키지

감사보고서 패키지(Audit Report Package)는 감사인의 의견이 적힌 본문만을
의미하지 않습니다.

```text
독립된 감사인의 감사보고서
+ 첨부된 감사대상 재무제표
+ 현금흐름표·자본변동표
+ 재무제표 주석 전체
+ 회계정책과 중요한 추정·판단
+ 핵심감사사항과 감사절차
```

따라서 재무제표, 재무제표 주석과 회계정책은 감사보고서 패키지를 기본
원천으로 사용합니다. 사업보고서에 유사 문구가 있어도 기본 원천으로
대체하지 않습니다.

### 함께 확인할 실제 예시

DART 제출물 하나를 열어 다음을 직접 찾습니다.

1. 감사보고서 본문
2. 감사의견
3. KAM
4. 첨부 재무상태표
5. 첨부 주석의 수익인식 회계정책
6. 해당 접수번호와 사업연도

그다음 같은 회사의 사업보고서에서 사업 내용과 매출구조를 찾아 두 원천의
역할이 다른 이유를 확인합니다.

## 7. 4부 — 전체 구조 설명

비개발자에게는 다음 비유로 설명합니다.

| 기술 요소 | 쉬운 설명 | 예시 |
|---|---|---|
| DART | 공식 원문 보관소 | 사업보고서·감사보고서 제출물 |
| Collector | 원문을 가져오는 수집 담당 | 접수번호로 XML·첨부파일 수집 |
| Parser | 원문을 제목·표·문단별로 나누는 코드 | KAM 제목과 감사절차 분리 |
| Database | 정리된 공용 자료함 | 회사·연도별 주석과 감사의견 저장 |
| Analysis | 업무 목적에 맞게 비교·계산하는 과정 | 현금흐름·Peer 비교 |
| MCP Server | 챗봇과 KReports 사이의 기능 연결자 | `get_audit_history` 호출 |
| Chatbot | 사용자가 질문하고 답을 보는 화면 | “매출 관련 KAM을 알려줘” |

전체 흐름:

```text
DART 원문
→ 수집
→ 보고서·첨부문서 구분
→ 필요한 문단·표 추출
→ 데이터베이스 저장
→ 검색·비교·분석
→ MCP 기능 호출
→ 챗봇 답변과 DART 원문 링크
```

자세한 내용은 `02_PROJECT_ARCHITECTURE_AND_DATA_FLOW.md`를 사용합니다.

## 8. 5부 — 데이터베이스 접근 방식

공용 데이터베이스는 KJ 한 명이 관리합니다.

- KJ: 수집, 데이터 저장, 구조 변경, 재생성, 출시용 DB 생성
- YE·EI: 공용 DB 전체 읽기 전용
- 전원: 개인 Test DB와 Fixture 생성 가능

읽기 전용(Read-only)은 데이터를 볼 수 없다는 뜻이 아닙니다. 승인된 주요
표와 원문 근거를 조회하고, 조회·분석·MCP 코드를 개발할 수 있습니다. 공용
데이터 값을 직접 덮어쓰지 못한다는 뜻입니다.

오류 발견 시:

```text
오류 사례 기록
→ Issue 생성
→ 원문과 기준 코드 확인
→ Collector·Parser·Analysis 수정
→ Test 추가
→ PR 제출
→ Review·Merge
→ KJ가 공용 DB 재생성
```

공용 DB 행을 손으로 고쳐서는 안 됩니다. 다음 수집이나 재생성에서 오류가
다시 발생하고 원인을 추적할 수 없기 때문입니다.

## 9. 6부 — GitHub 개념과 실습

### 핵심 개념

- Issue(업무와 완료조건을 기록하는 작업표)
- Assignee(해당 업무의 주 책임자)
- Branch(`main`과 분리된 하나의 업무 작업선)
- Worktree(특정 Branch를 실제 파일 폴더로 연 작업공간)
- Commit(특정 시점의 변경 기록)
- Push(Commit을 GitHub에 올리는 작업)
- PR(변경을 `main`에 합쳐도 되는지 검토받는 요청)
- Review(승인·질문·수정 요청)
- Merge(승인된 변경을 `main`에 반영)

### 작업단위 원칙

```text
하나의 Issue
→ 하나의 작업 Branch
→ 하나의 Primary Assignee
→ 하나의 PR
```

신규 업무에는 `kj`, `ye`, `ei`와 같은 사람별 장기 Branch를 사용하지
않습니다.

Branch 예:

```text
feat/10-audit-package-note-source
feat/11-business-report-analysis
fix/15-wrong-dart-link
```

### 실습 순서

1. 첫 Issue 읽기
2. 사용자 문제와 완료조건 설명
3. 최신 `main` 확인
4. Issue용 작업 Branch 생성
5. 해당 Branch의 Worktree 열기
6. 상태 문서 한 줄 수정
7. `git status`와 `git diff` 확인
8. 확인한 파일만 Stage
9. Commit
10. Push
11. Draft PR 생성
12. 다른 사람의 PR에서 Review 화면 확인

### 수정 요청 실습 설명

PR에서 수정 요청을 받아도 Worktree를 원복하지 않습니다.

```text
같은 작업 Branch에서 수정
→ Test 재실행
→ 새 Commit
→ 같은 Branch로 Push
→ 기존 PR 자동 업데이트
```

### Merge 후 설명

PR이 Merge돼도 로컬 Worktree가 자동으로 최신 `main`이 되지는 않습니다.
완료된 Branch와 Worktree를 정리하고 다음 Issue는 최신 `main`에서 새 Branch로
시작합니다.

상세 내용은 `03_GITHUB_WORKFLOW.md`를 사용합니다.

## 11. 8부 — AI 빌딩 작업 방식

AI 빌딩은 다음 순서를 지킵니다.

```text
사용자 문제 정의
→ 기존 코드와 데이터 흐름 조사
→ Reuse Map 작성
→ 작은 변경안 설계
→ AI와 구현
→ 자동 Test
→ 실제 DART 원문 대조
→ PR과 Review
→ 챗봇 시연
```

AI에게 바로 “기능을 만들어줘”라고 요청하지 않습니다.

권장 요청 예:

```text
현재 이 기능의 E2E 흐름과 기존 기준 코드를 먼저 찾아줘.
같은 역할을 하는 함수·SQL·Parser를 새로 만들지 말아줘.
수정할 파일, 재사용할 코드와 필요한 Test를 구현 전에 설명해줘.
```

AI 제안을 그대로 채택하지 않은 부분과 그 이유도 상태 문서와 PR에
기록합니다.

## 13. 10부 — 제출자료와 개발 결과 연결

개발 과정의 산출물을 제출자료로 재사용합니다.

| 개발 산출물 | 제출자료 활용 |
|---|---|
| 현재 수작업 흐름 | 문제 상황 |
| Architecture·E2E 흐름 | 아이디어 핵심 내용 |
| 챗봇 화면 | 90초 영상·구체화 결과 |
| 실제 DART 비교표 | 구현 신뢰성 |
| 자동 Test 결과 | 구체화 수준 |
| 탐색시간 측정 | 기대효과 |
| 알려진 한계 | 현재 범위·향후 고도화 |

영상, Word 설명서와 화면은 동일한 Commit SHA, Runtime DB, 회사·연도와
Scenario를 사용해야 합니다.

## 14. 첫 과제

### YE 첫 과제

대표회사 하나를 기준으로 다음 흐름을 설명합니다.

```text
사업보고서 본문
→ 사업·제품·매출구조·위험 추출
→ DB
→ Analysis
→ MCP
→ 챗봇 답변·원문 링크
```

산출물:

- 사용자 질문
- 현재 결과
- 관련 코드·DB 표·MCP Tool·Test
- 실제 사업보고서와 차이
- 첫 개선 Issue와 완료조건

대표회사 하나를 기준으로 다음 흐름을 설명합니다.

```text
감사보고서 제출물·첨부
→ 재무제표·주석·KAM·감사절차 선택
→ DB
→ Analysis
→ MCP
→ 챗봇 답변·원문 링크
```

산출물:

- 사용자 질문

- 실제 감사보고서 패키지와 차이

## 15. 오리엔테이션 종료 확인

각 참석자가 다음 질문에 답합니다.

1. KReports는 무엇을 해결하는가?
2. 재무제표 주석은 어느 보고서를 기본 원천으로 하는가?
3. 공용 DB 오류를 발견하면 어떻게 처리하는가?
4. MCP는 어떤 역할을 하는가?
5. Branch는 사람별인가, 작업별인가?
6. PR에서 수정 요청을 받으면 Worktree를 원복하는가?
7. Merge 후 다음 업무는 어느 기준에서 시작하는가?
8. 자신의 첫 Issue와 완료조건은 무엇인가?
9. AI가 만든 결과를 어떤 Test와 실제 자료로 확인할 것인가?
10. 자신의 개발 결과가 영상과 Word 설명서의 어느 부분에 사용되는가?

모든 질문을 완벽히 기술적으로 답할 필요는 없습니다. 다만 자신의 기능이
어떤 원천에서 시작해 어떤 사용자 결과로 이어지는지 설명할 수 있어야
합니다.
